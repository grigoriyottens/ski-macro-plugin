# Отбор договоров, а не всех документов

Прочитай для списков, подсчётов и выбора «любого договора». Для файла уже выбранной карточки не начинай повторный реестр. Это рабочая классификация СКИ, не юридическое заключение о заключённости документа.

## Что означает запрос

- «Договоры» без уточнения: самостоятельные основные договоры, включая государственные контракты. Приложения, спецификации, допсоглашения, протоколы, счета и заявки не считаются отдельными договорами.
- «Все документы», «договор и приложения», «допсоглашения» — другой охват; выполни его, обозначив виды документов и доступные связи.
- Счета-оферты и оферты по умолчанию не смешивай с основными договорами; включай отдельной категорией по запросу. Это не утверждение, что они не могут иметь договорную силу.
- «Пять» означает пять подходящих примеров. Не обещай «последние» без запроса. Для «последних» согласуй или явно обозначь дату отбора и обеспечь соответствующую сортировку; первая страница по ID не доказывает новизну.

## Доступные признаки

Схема проверена 18.09.2026; перед запросом проверь актуальную спецификацию сервера.

MacroData: `contacts_agreements` содержит `company_id`, `projects_id`, `contacts_agreements_id`, `types_id`, `type_name`, `document_kind`, `parent_id`, `agreements_title`, `agreements_num`, `agreements_date`, `agreements_sum`. Не путай внутренний `id` строки с бизнес-идентификатором документа `contacts_agreements_id`. При передаче в API проверь соответствие карточки. Связи устанавливай по схеме, не по сходству чисел.

| Значение document_kind | Значение для отбора |
|---|---|
| `addons_type_not_addon` | Основной документ: кандидат, но НЕ доказательство договора. |
| `addons_type_standalone` | Самостоятельный документ: кандидат, но НЕ доказательство договора. |
| `addons_type_subject_empty` | Допсоглашение без предмета; отдельно от основных договоров. |
| `addons_type_parent_changing` | Допсоглашение, меняющее предмет родительского договора. |
| `addons_type_subject_own` | Допсоглашение со своим предметом; не самостоятельный основной договор. |

Непустой `parent_id` указывает на связанность; проверь вид связи. Пустой `parent_id` не доказывает самостоятельный договор: встречаются приложения, записанные как основной документ без родителя. `type_name` — пользовательская категория, иногда широкая или ошибочная. Объект определяй по связи `projects_id`, не по названию категории. Не зашивай клиентские `types_id` в правила без проверенного справочника.

В проверенных ответах API `documents.list/get` есть название, номер, проект, сумма и `typeName`, но нет стабильных `document_kind`, `parent_id` и `types_id`. Не передавай выдуманные фильтры этих полей в API. Каталог текущей сессии может отличаться — сверяй схему.

## Алгоритм

1. Зафиксируй компанию и объект из контекста проекта или пользователя. ID MacroData не переноси в другие сущности без проверки. Не расширяй охват молча.
2. До вызовов выбери доступную цепочку: MacroData для реестра с метаданными; API для конкретной карточки/файла. При установленном только API можно изначально выбрать ограниченную выборку API. Ошибка одного подключения не разрешает переключиться на другое.
3. Сопоставь вид, родителя, тип и смысл названия. «Приложение к договору» не договор, хотя слово «договор» есть. «Государственный контракт» может быть договором без этого слова. Несогласованность полей не скрывай.
4. Основной/самостоятельный вид и пустой родитель — только первичный фильтр. Отбрасывай явно названные приложения и другие исключённые виды даже после этого фильтра. Не используй только `LIKE '%договор%'`, сумму больше нуля, согласование или наличие файла как классификатор.
5. При неоднозначности проверь карточку и, если необходимо, конкретный файл через заранее предусмотренный API. Если доказательств недостаточно, оставь «тип не подтверждён» вне подтверждённого количества. Для списка не скачивай массово все вложения.
6. Сначала классификация, затем итоговые N. Запрос одной порции `LIMIT N` общих документов не гарантирует N договоров. Выбирай небольшие порции кандидатов в устойчивом порядке, продолжай по реальной пагинации без повторов ID. Для простого запроса примеров начни с 30 кандидатов (или меньшего серверного лимита), не превышай 3 порции без согласования расширения. Если подтверждено меньше N — покажи меньше и границу, не дополняй спецификациями. Для полного подсчёта/последних договоров этот быстрый неполный просмотр не подходит: нужна полная релевантная выборка/корректная агрегация; при лимитах не обещай полноту.
7. Для API без структурных признаков явно называй отбор предварительным по карточкам, если независимость не подтверждена. Если явно положительные сведения достаточны для примеров, не блокируй весь запрос из-за отсутствия MacroData. Для точного числа договоров не выдавай эвристику по названиям за достоверную классификацию.

## Суммы и статусы

Ноль не делает карточку недоговором или бесплатным договором. В проверке сумма MacroData и сумма API для одной карточки различались; причина не установлена. Не считай эти поля взаимозаменяемыми, не называй расхождение автоматически задержкой синхронизации. Для оперативной суммы используй API с проверкой смысла поля; для аналитического итога укажи источник/срез/определение суммы. Не складывай основной договор с его приложениями и допсоглашениями без правила изменения стоимости. «Согласование завершено» не доказывает подпись или вступление в силу.

## Короткий ответ

«Нашёл 5 основных договоров» — только при соответствующем отборе. Если показаны кандидаты, так и назови. Дай номер/название, контрагента, запрошенные поля и достаточную идентификацию карточки. Не показывай нулевую сумму как установленную стоимость при противоречиях. Для неполного результата: «Подтвердил 3 договора в просмотренной выборке; приложения и спорные карточки не включал».
